# Diabetes Patient Management - Readmission Care Queue (Week 3)

FDE Program homework: a FastAPI + PostgreSQL backend and a TypeScript web UI for finding patients,
spotting high-risk encounters and tracking the follow-up status of each one.

> **Learning prototype.** The risk score is a simple, explainable set of learning assumptions. It is not
> clinically validated and must not be used for real patient care decisions.

## 1. Objective
A hospital has historical diabetes encounter data and wants the care-management team to follow up first with
the patients most likely to return within 30 days. This project lets a care coordinator:

1. **Search** encounters by patient number, risk level and/or risk score.
2. **Open** an encounter from the results and see its current care status.
3. **Update** the status (who it is assigned to, notes) and see the update listed.

**Learning goals:** build a layered Python API (`main.py` -> `service.py` -> `repository.py` -> PostgreSQL), test it
in Swagger, then call it from a typed TypeScript frontend running in the browser.

## 2. Screens
| Screen | File | What it does |
| :--- | :--- | :--- |
| 1. Search Patient | `frontend/search.html` | Filters: Patient Number, Risk Level (dropdown), Risk Score. Results table; each **Encounter Id is a link** to screen 2. |
| 2. Status Tracking | `frontend/status.html` | Shows Encounter Id and Patient Number (read-only), plus Status (dropdown), Assigned To and Notes. **Update** saves the change and adds it to the Updates list. |

## 3. Architecture
```
Healthcare CSV -> data_loader.py -> PostgreSQL <- repository.py <- service.py <- main.py (FastAPI) <- frontend (TypeScript)
```
| File / folder | Role |
| :--- | :--- |
| `main.py` | Routes, input limits, CORS, error handlers |
| `models.py` | Pydantic models and enums (`RiskLevel`, `InterventionStatus`) |
| `service.py` | Business rules: risk scoring, "closed cases stay closed", status lookup |
| `repository.py` | All SQL. Every value is a bound parameter (no string-built values) |
| `database.py` | Reads `DATABASE_URL` from `.env`, 5-second connect timeout |
| `data_loader.py` | Loads the CSV into PostgreSQL and scores each encounter |
| `schema.sql`, `seed_or_setup.sql` | Tables and one-time user/database setup |
| `frontend/src/*.ts` | TypeScript source: `config.ts`, `types.ts`, `api.ts`, `dom.ts`, `search.ts`, `status.ts` |
| `frontend/dist/` | Compiled JavaScript the browser loads (generated by `npm run build`) |
| `frontend/serve.mjs` | Tiny local web server for the pages (port 5500) |
| `test_api_qa.py` | Automated tests inherited from the earlier project (see section 8) |

## 4. Data and risk score
Source: `diabetic_data.csv`, 101,766 encounters (kept out of git because it is patient data).

| Condition | Points |
| :--- | :--- |
| `number_inpatient >= 3` | +3 |
| `number_emergency >= 2` | +2 |
| `number_outpatient >= 3` | +1 |
| `time_in_hospital >= 7` | +1 |
| `num_medications >= 20` | +1 |

Risk score is **0 to 8**. Level: **0-2 = LOW, 3-4 = MEDIUM, 5+ = HIGH**. The historical `readmitted` value is never
used to calculate the score.

## 5. Database (PostgreSQL)
- **`patient_encounters`**: the dataset fields plus `risk_score` and `risk_level`.
- **`care_interventions`**: one row per encounter - `status`, `assigned_to`, `notes`, `created_at`, `updated_at`.
  An encounter with no row is shown as `PENDING_REVIEW`.
- Status workflow: `PENDING_REVIEW -> ASSIGNED -> CONTACTED -> FOLLOW_UP_SCHEDULED -> CLOSED`.
  A `CLOSED` case cannot be reopened.

## 6. API
Swagger UI: http://127.0.0.1:8001/docs (when started on port 8001, see section 7).

| Method | Endpoint | Purpose |
| :--- | :--- | :--- |
| `GET` | `/patients/search` | **Screen 1.** Filters `patient_nbr`, `risk_level`, `risk_score` (all optional, combined with AND), plus `limit` / `offset`. Highest risk first. |
| `GET` | `/interventions/{encounter_id}` | **Screen 2.** Encounter, patient number, risk and current care status. `404` if the encounter does not exist. |
| `PATCH` | `/interventions/{encounter_id}` | **Screen 2.** Save `status`, `assigned_to`, `notes`. `409` if the case is already `CLOSED`. |
| `GET` | `/encounters`, `/encounters/{encounter_id}` | List (paged) or fetch one encounter |
| `GET` | `/patients/{patient_nbr}/encounters` | All encounters of one patient |
| `GET` | `/care-queue`, `/care-queue/high` | Open MEDIUM + HIGH queue, or HIGH only |
| `GET` | `/operations/summary` | Counts by risk level, pending and completed interventions |
| `GET` | `/operations/readmission-analysis` | 30-day readmission rate per risk group |
| `GET` | `/analytics/age-groups`, `/analytics/utilization` | Readmission by age band and by prior inpatient visits |
| `GET` | `/management/dashboard` | Operations + readmission analysis in one call |

Search behaviour: `patient_nbr` and `risk_score` are exact matches; `risk_level` is `LOW`, `MEDIUM` or `HIGH`; invalid
values return `422`; a search with no filters returns the first page of all encounters.

Example update (`PATCH /interventions/116415312`):
```json
{ "status": "CONTACTED", "assigned_to": "Care Team A", "notes": "Follow-up call made" }
```

## 7. How to run
**Prerequisites:** Python 3.11+, Node.js 22+ (with npm), and a running PostgreSQL server.
All commands below are run from this folder (`HW_Week3_Healthcare_HW`) unless stated.

### 7.1 Backend (API)
1. Create and activate a virtual environment, then install the packages:
   ```
   python -m venv .venv
   .venv\Scripts\activate          (Windows)   |   source .venv/bin/activate   (macOS/Linux)
   pip install -r requirements.txt
   ```
2. Create the database user and database (edit the password inside the file first):
   `psql -U postgres -f seed_or_setup.sql`
3. Copy `.env.example` to `.env` and set `DATABASE_URL` (same password). **Never commit `.env`.**
4. Create the tables: `psql -U fde_user -d fde_db -f schema.sql`
5. Put `diabetic_data.csv` in `data/`, then load and score it (about 5 seconds): `python data_loader.py`
   (skip steps 2-5 if you are using the database that is already loaded).
6. Start the API on port 8001:
   ```
   uvicorn main:app --host 127.0.0.1 --port 8001 --reload
   ```
   Open http://127.0.0.1:8001/docs and try `GET /patients/search` (for example `risk_level=HIGH`).

### 7.2 Frontend (TypeScript UI)
In a second terminal:
```
cd frontend
npm install          (first time only - installs TypeScript)
npm start            (compiles src/*.ts to dist/*.js, then serves the pages on port 5500)
```
Open **http://localhost:5500/search.html** in the browser.

Useful commands in `frontend/`: `npm run build` (compile once), `npm run watch` (recompile on save),
`npm run serve` (serve without compiling).

### 7.3 Using the app
1. On **Search Patient**, enter a Patient Number and/or choose a Risk Level and/or enter a Risk Score (0-8), then click **Search**.
2. Click an **Encounter Id** in the results to open **Status Tracking**.
3. Pick a Status, optionally set Assigned To and Notes, then click **Update**. The change appears in the Updates list.

### 7.4 Configuration
| Setting | Where | Default |
| :--- | :--- | :--- |
| API address used by the pages | `frontend/src/config.ts` (`API_BASE_URL`) | `http://127.0.0.1:8001` |
| Rows per search | `frontend/src/config.ts` (`SEARCH_PAGE_SIZE`) | 50 |
| Database connection | `.env` (`DATABASE_URL`) | none - you must set it |
| Browsers allowed to call the API | `main.py` (`ALLOWED_ORIGINS`) | `localhost` / `127.0.0.1` on ports 3000, 5173, 5500 |

After changing `config.ts`, run `npm run build` again. If you serve the pages on a different port, add that origin
to `ALLOWED_ORIGINS` and restart the API, otherwise the browser blocks the calls (CORS).

## 8. Testing
- **Manual / Swagger:** `/patients/search` and `/interventions/{encounter_id}` were exercised for valid filters,
  combined filters, no matches, invalid values (`422`), an SQL-injection string (treated as plain text), unknown
  encounters (`404`) and the closed-case rule (`409`).
- **Frontend:** the TypeScript compiles in strict mode with no errors, and the compiled API client was run against the live API.
- **Automated suite:** `test_api_qa.py` (`python -m unittest test_api_qa -v`, needs `pip install httpx` and a
  reachable PostgreSQL) comes from the earlier project. It has **not** been updated or re-run for the new
  `/patients/search` and `GET /interventions/{encounter_id}` endpoints yet.

## 9. Known limitations and next steps
- **No update history.** The database keeps one row per encounter and overwrites it on each update, so the Updates list
  shows the latest saved record plus the updates made during the current visit. A true history needs a new table.
- **No "create encounter" endpoint**, so new encounters cannot be added from the UI.
- **High-care list screen** (list only HIGH-risk patients with their intervention status) is not built as its own
  screen yet; use Search with Risk Level = HIGH, or the `/care-queue/high` API.
- No login or user roles - anyone who can reach the API can read and update records.
- Add tests for the new endpoints and pagination controls on the results table.

*Learning use only - not for clinical decision-making.*
